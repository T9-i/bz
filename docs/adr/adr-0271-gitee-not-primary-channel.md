# ADR-0271：码云不作下载主通道，只作镜像备份与次级通道

- 状态：已采纳（2026-10-29 用户提议，核查后按「不拆库、不换主通道」落地）
- 日期：2026-10-29
- 相关：ADR-0269（独立分发仓库 `yeshimei/bz-assets`）、ADR-0263（外部工具分发与指针）

## 背景

用户提的两个问题：

1. 「外部工具和在线资源放到码云是不是也可以？」
2. 「把 bz 在码云提交一份，这样不用额外拆一个库？」

动机是实在的：`bz-assets` 是为此专门拆出来的第二个仓库，多一个仓库就多一处要记得推。
而码云在国内裸网可达——这正是 ADR-0269 里 raw 与 jsDelivr 都死掉的那件事的正面答案。

## 核查事实

码云社区版配额（官方帮助中心「使用配额说明」/「仓库体积过大，如何减小」）：

| 项 | 上限 | 对本项目的含义 |
|---|---|---|
| 单仓库 | 500 MB | 主仓 `.git` 现 **283 MB**（`size-pack` 282.68 MiB），只剩 ~200 MB 余量 |
| 单文件 | 50 MB | 现有产物最大的是 `main.js`（~2 MB）与目录包 tar.gz，都远低于此 |
| 单次 HTTP push | 200 MB（超限返回 413） | **首次整仓推送走 HTTPS 必被拒**，得用 SSH 或分批推 |
| 用户总仓库 | 5 GB | 够用 |

另外两条影响更大：raw 直链在码云上不是为「第三方程序批量下载」设计的（历史上有防盗链与
频控），而 `releases/<tag>/` 下的三件套是自更新链路的关键路径——把它押在一条随时可能因为
防盗链策略变动的直链上，等于把「装不上新版」的概率换成了不可控项。

## 决策

**不拆新库、不换主通道；码云作为同一仓库的镜像目标保留可能性，主通道仍是 `bz-assets`。**

- 一个仓库同时装源码与 `downloads/**` 这件事本身**可行**（283 MB < 500 MB），用户说的
  「不用额外拆一个库」在容量上成立。
- 但「可行」不等于「该现在做」：主仓每发布一版就往历史里多压一份 tar.gz 与插件本体三件套，
  283 MB 的余量挡不住几个月的发布节奏；而码云不像 `bz-assets` 那样可以「删掉重建」——
  主仓历史不能压平。
- 真要加码云通道，正确形态是 **镜像脚本多一个目标**（把 `downloads/**` 与 `releases/<tag>/`
  推到「同一个仓库」的对应路径），客户端在 `src/core/remote-base.ts` 里多一条 base，
  下载器按通道顺序 fallback。**现在不做**：没有实测数据支撑它比 `bz-assets` 更快或更稳，
  先加一条没人验证的通道，只是把排查面从两条变成三条。

## 什么时候重做这个决定

出现下列任一事实就重新评估：

- `bz-assets` 在国内裸网再次不可达（ADR-0269 的实测已过期）；
- 主仓 `.git` 涨过 400 MB（余量不足），届时「同库镜像」这条路自然关闭；
- 码云提供明确面向程序下载的发行版直链（非 raw、非网页中转）。

## 后果

- 发布链路不变：`push-assets` 只推 `yeshimei/bz-assets`。
- 想在码云留一份源码备份，走的是「普通镜像」，与下载链路无关，不影响任何代码。
