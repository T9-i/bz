# ADR-0242 · 工具坞：离线值守进程（dock-watch）—— 判据复用、租约互斥、离场记账

日期：2026-10-14 · 状态：已采纳 · 关联：ADR-0235（外部工具契约）、ADR-0236（bz 亲自调度）、
ADR-0237（文件名惯例）、ADR-0239（面板数据与信任分家）、`docs/dock-tool-guide.md`

## 背景

ADR-0236 让 bz 亲自调度自动化工具，但**调度器住在插件进程里**：Obsidian 不开，规则表就是一张纸。
「每天 12:00 那个签到」只要当天没开过 Obsidian，就不会跑。

用户提出的落点：

> 增加一个脚本，挂在 windows 的自启动，作为监听工具坞脚本自动化执行的入口，
> 实现不用启动 obsidian 也可以按时执行自动化脚本的功能。

这件事有个**已经写死的阻碍**：`docs/dock-tool-guide.md` §7 明说「有启用中规则的工具别再配一份
系统计划任务（两个触发源，记录翻倍）」。那条不是洁癖，是实数 —— 两个调度者各判各的、各记各的账，
同一个工具一天会被跑两遍，而且**两边都不觉得自己错**。

所以本轮真正的题不是「怎么挂自启动」，而是「**怎么让第二个调度者与第一个共存**」。

## 决策

### 1. 形态：一个常驻进程，不是又一份计划任务

新增 `tools/dock-watch/`（零外部依赖的 node 子包），由安装脚本挂到 Windows 登录自启上，
**每 30 秒一拍**（比插件的 60 秒快一倍 —— Obsidian 刚关掉时能尽快接管）。

它**不是工具坞里的一个工具**：工具坞工具是「被调度方」（manifest + 四行协议 + runs.json），
而它要反过来调度别人 —— 它是**调度方**。把它登记进去会立刻自指（规则表指向自己、面板上多一张
会被自己调度的卡），所以面板只给它一条**只读**的状态条，不进登记表。

会话态住 `%LOCALAPPDATA%\bz-dock-watch\`（**不进 vault**）：租约每 60 秒变一次，
放进 vault 等于把 git 与同步盘的状态天天搅脏。

| 文件 | 谁写 | 作用 |
|---|---|---|
| `config.json` | 安装脚本 | vault 根 / 拍间隔 |
| `lease.json` | **bz 插件** | 「插件在场」的声明（见 §3） |
| `status.json` | 值守进程 | 每拍刷新的体检快照（面板那条读它） |
| `pending.json` | 值守进程追加 | 离线跑过什么；插件首次打开面板时弹一次简报（见 §8） |
| `watch.lock` | 值守进程 | 单实例锁 |

### 2. 判据**复用**，绝不复刻

值守进程要回答「这条规则此刻该不该跑」，而这个答案**只有一份**：`src/dock/rules.ts` 的 `ruleDue`
（纯函数，零依赖）。复刻一份就是两套真理源 —— 一边改了边界条件（比如 `interval` 首次无基线该不该
跑），另一边的实现不知道。

做法：新增 `src/dock/watch-core.ts`（**只做再导出**），由 `scripts/build-dock-watch.mjs` 用 esbuild
把它打成 `tools/dock-watch/dock-core.cjs`，值守进程 `require` 过去。

- 只许再导出 `schema` / `schedule` / `rules` / `registry` / `declaration` 五个零依赖纯模块。
  一旦塞进碰宿主的模块，`obsidian` 会被打进产物 —— 打包脚本**自带守门**：
  产物里出现 `obsidian` 就删掉产物并报错（症状否则会推迟到用户机器上「值守一启动就崩」）。
- 用具名导出而非 `export *`：五个模块之间有同名导出（`durationText` 在 `rules` 与 `schedule` 里
  各有一份），`export *` 撞名会变成有歧义的导出。
- 产物**入 git**（生成物但跟踪，同根 `main.js` / `changelog-data.ts`）：`tools/` 下的子包要能单独
  拿出去用。改判据 → 重跑 `node scripts/build-dock-watch.mjs`（已挂进 `pnpm run build` 的
  production 分支）。

**可验证性**：`tests/dock/watchdog.test.ts` 里有一条用例直接 `require` 值守侧的 `runtime.js`，
断言两边的目录推导逐字相同 —— 「约定」必须能被测试盯住，否则它只是一句注释。

### 3. 互斥：一张租约，插件单向声明，值守严格让位

| 侧 | 行为 |
|---|---|
| 插件 | `startDockScheduler` 装载时写一次租约（不写的话，首拍前那 3 秒会被值守抢一拍）、每次 tick 续一次、`stopDockScheduler` 撤票 |
| 值守 | 只在租约**不新鲜 / 不属于本 vault / pid 已死**时才拍，否则记 `mode: defer` 后让位 |

三个判据缺一不可，其中第三条是多 vault 同机的关键边界：**用户在 vault A 开着 Obsidian，值守配的是
vault B** —— 若不比对 vault，A 的插件会把 B 的规则「让位」掉，B 整天不跑而两边都不报错。

- 租约**不受总闸影响**：「插件在场」是事实，与自动运行开不开是两件事（值守自己会查开关）。
- 撤票不需要等 TTL：`stopDockScheduler` 删掉文件，值守下一拍（≤30 秒）立刻接管。
- 第二道防线是**共享记账**：`lastFiredAt` 就在同一份 `dock.json` 里，谁先记账谁跑。
  残余窗口只剩「两边同时读到未记账 → 都记账 → 都跑」，宽度是读写之间的那几十毫秒，
  且只在「插件恰好启动/退出的那一瞬」才可能撞上 —— 这是本方案接受的代价，不是遗漏。

### 4. 开关分两层：`autoRun`（行为）与 `watchdog`（离场那一半）

新增 `dock.json` 的 `watchdog`（缺省开），与既有的 `autoRun` 并列但不同层：

- `autoRun` 是**「自动运行」这个行为的开关**，在场离场都管（值守进程也读它）；
- `watchdog` 只管**离场那一半**让不让值守接手。

**两个都开才离场跑。** 这样「关掉自动运行 = 彻底不自动跑」的语义保持单一 —— 否则会出现
「面板上写着自动运行：关，但电源一断它还是跑了」，那是用户永远查不出来的那种 bug。

面板与设置的控件不并列同一件事：**开关只在「设置 → 工具坞 → 自动运行」**，面板那条只读。

### 5. 离线能力边界（写死在文档里，不靠用户自己发现）

| 触发 | 离场 | 为什么 |
|---|---|---|
| `daily` / `interval` | ✅ | 主力场景，靠时钟 |
| `data-threshold` | ✅ | 直读 vault 里的 json 数值 |
| `tool-ok` / `tool-fail` | ✅ | 值守自己跑完接着判联动，防环规则照旧 |
| `on-launch` | ❌ | 语义是「Obsidian 启动后」；硬套成「值守启动后」会让同一条规则一天跑两次 |
| `panel-open` | ❌ | 没有面板 |
| `domain-event` | ❌ | 总线在插件进程里 |
| `vault-file` | ❌（第一版） | 需要 fs.watch 与节流；**没有事件时 `ruleDue` 自然返回 false**，安全跳过而不是乱跑 |

`on-launch` 的排除是**免费**的：不传 `sessionStart` 给 `ruleDue`，它的那条分支自己就返回 false ——
不需要在值守里写一个「跳过 on-launch」的判断（那种判断正是会漂的东西）。

### 6. 离场语义：环境与参数逐字同插件，记录照旧不代写

三处刻意与 `runner.ts` 逐字一致（「同一个工具在面板里能跑、关掉 Obsidian 就跑不起来」是双层实现
最贵的缺陷）：

1. **环境变量只给那五个**（`BZ_DOCK_CONTRACT/TOOL/RUNS_FILE/VAULT/TRIGGER`，不继承宿主）。
   多塞一个 `PATH` 会让某些工具在值守下侥幸成功、在插件下失败。
2. **参数下发走 `buildArgs`**（同一份实现）；`cwd` 缺省 = 工具目录。
3. **10 分钟超时强杀**（`taskkill /T /F`，Windows 上经 shell 起的 `.cmd` 要连壳一起收）。

| 事 | 谁做 |
|---|---|
| 运行记录 `runs.json` | **只有工具自己**（D8/D9 不变；跑完值守只**回读**它，取工具留的那句话进队列） |
| 规则记账 `lastFiredAt` | 值守写（跑**之前**写，否则下一拍重复命中） |
| 台账 `runState`（失败计数 / 熔断） | 值守写 —— 离场跑失败不入账就会重试到天亮 |
| `remind`（只提醒） | **记账但不投递**：提醒的价值在「当时」，隔一天补一条只是噪音 |

`BZ_DOCK_TRIGGER` 恒为 `auto`：离场这一路就是自动触发（面板手点只可能发生在插件里）。

### 7. `dock.json` 从此有两个写者

这是本决策**要认的代价**。缓解三层，全部落地：

1. **互斥保证同一时刻只有一个在拍**（§3）—— 真实并发窗口只剩「插件恰在启动/退出的一瞬」；
2. **每次写都先重读文件**（不拿主循环手上那份快照改），把窗口缩到「读与写之间」这段同步代码。
   **这段代码里没有一个 `await`**（`readFileSync` → 改 → `renameSync`），所以在单个进程内它不可被
   打断 —— 冲突只可能来自另一个进程，而那个进程在那一刻正被租约挡着。这不是侥幸，是「不做段级
   合并写」的依据；
3. **只改自己那一块 + 原子写**（tmp + rename），且 `{...raw, tools}` 这种写法保证**本进程
   不认识的字段原样留着**（未来版本加的字段不能被旧值守删掉）。

> 已知不对称（本轮不改，记在这里）：插件侧的 `normalizeDockStore` 只回填认识的键，它写盘时会
> **丢掉** `dock.json` 顶层未来版本新增的字段；值守侧保留。要让两边对称得改 `store.ts` 的归一与
> 写入口，那是独立的一件事，不该混在这次里。

不做段级合并写（那是 `news.json` / ADR-0128 的教训留下的重武器）—— 三层缓解已把风险压到「重复跑
一次」量级，而上一条 ADR-0239 的分家理由在这里不适用：这一份文件**本来就该被两个进程读**。

### 8. 交代：独立弹窗简报，不引系统通知

Obsidian 没开时通知发不出。值守把每次离场运行追加进 `pending.json`，**打开工具坞面板时用一个独立
弹窗交代一次**（`uiModal` 承载）：抬头是「跑了 N 次 · X 成功 Y 失败 · 起止时刻」，下面一行一个工具
（次数、成败、最近一次在什么时候、失败原因）。

**不逐条弹通知**：好几天的账拆成五条 toast 再加一句「另有 N 次」，既糊脸又读不出全貌 —— 而「这段
时间成没成、哪个工具掉了」正是要一眼看完的东西，弹窗一次说完比通知刷屏更省用户的事。

**不设第二把开关**：主动打开面板才看得到的东西不是「提醒」，不受 `notifyMissed` 管（那把只管
「该跑没跑」）。弹窗**纯只读**，不给任何后续动作按钮 —— 该不该重跑由每个工具自己的规则表说了算。

消费走「先重读再删，**只删自己播过的**」：值守可能正在追加新条目，整文件覆写会把它们一起抹掉。
队列消费完这个弹窗自然就不再出现 —— 「首次打开才交代」是消费的副产物，不是另记一个已读水位。

同样**不引 Windows toast**：绕开 `core/notice.ts` 的文案口径（不带动效、正文不带 emoji）不值得，
而且用户专注时并不想要系统级弹窗。

### 9. 安全：信任门照旧，离场不打折

值守读插件设置 `data.json` 的 `dockTrust`，并做**同一把 `runSignature` 比对**：没信任过、
命令改过（`trustStale`）→ 不跑。离场执行同样是「在他机器上执行命令」，ADR-0235 的边界不因
没人看着而放宽。

## 明确不做

- **不把值守进程登记成工具坞工具**（它是调度方，登记即自指）。
- **不新增环境变量**（比如标识「这次是离场跑」）：契约 §4.1 是封闭的，多一个变量就多一处
  两边可能不一致的地方；「谁拉起的」由 `watch.log` 与 `runs.json` 的时间戳回答。
- **不代写 `runs.json`**（记录的唯一写者始终是工具）。
- **不在面板上放第二个开关**（开关只在设置页）。
- **不做 `vault-file` 触发**（第一版；没事件时规则自然不命中）。
- **不做「值守进程自己维护一份规则缓存」**：每拍现读 `dock.json`，外部改了下拍即生效（同 ADR-0239
  「不缓存声明」的精神）。

## 后果

- 新增：`src/dock/watchdog.ts`（插件侧租约/状态/队列接口）、`src/dock/watch-core.ts`（再导出面）、
  `scripts/build-dock-watch.mjs`、`tools/dock-watch/`（进程本体 + 安装脚本 + 自带测试）。
- 插件侧改动三处：`scheduler.ts` 写/撤租约（几行）、`store.ts` 加 `watchdog` 开关、
  `ui.ts` 加只读值守条与离线简报弹窗；`settings.ts` 加「离线值守」一行（**装没装决定它是开关还是一句话**）。
- `dock.json` 多一个字段、多一个写者（§7 的三层缓解）。
- **要认的代价**：
  - 改判据必须重跑打包脚本（已挂进 `pnpm run build`），否则值守用的还是旧判据 ——
    产物里带了打包时的 bz 版本，面板与 `status.json` 都比对它，不一致时能看出来；
  - `docs/dock-tool-guide.md` §7 那句「别再配系统计划任务」要改口 —— 现在官方值守件就是那个
    「第二触发源」的正解，而它靠租约与共享记账与插件共存。
- 参考实现 `iamtxt-signin` 不需要任何改动即可在离场跑起来（契约没变）。
