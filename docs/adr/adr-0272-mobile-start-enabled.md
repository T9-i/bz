# ADR-0272：放行移动端启动（推翻 ADR-0263 §5）

- 状态：已采纳（2026-10-29 用户报障「移动端无法启动 bz」）
- 日期：2026-10-29
- 相关：ADR-0263 §5（原决定 `isDesktopOnly: true`）、`core/mobile.ts`、`dock/vault-fs.ts`

## 背景

用户报：手机上装好 bz，插件起不来。

查下来的事实很干脆——`manifest.json` 里写着 `"isDesktopOnly": true`。这不是「启动后崩」，
是 **Obsidian 在移动端根本不加载**：第三方插件列表里这一项不可启用，用户看到的是「装不上」。

而这个开关与两处既有事实互相矛盾：

1. `README.md` 第 6 行：「**桌面端 + 移动端**通用（要求 Obsidian ≥ 1.4.0）」，第 257 行还有
   整整一节「移动端」，写的是「手机和平板上功能完整可用」，并承诺「少数依赖本地外部程序的
   能力仅桌面端可用……对应设置会置灰标注，不做静默降级」；
2. 代码侧早就在为移动端做事，不是「没打算支持」：
   - `core/mobile.ts`：`isMobileEnv()`，全仓统一口径；
   - `dock/vault-fs.ts`：`installVaultFs()` —— 手机没有 Node，`window.require('fs')` 那条读链
     整条是断的，于是打开库时用 vault 适配器把登记表与工具文件预取进内存，再把 fs 缝到内存上，
     工具坞「只读面板」在手机上照样能看；
   - 各域 UI 大量 `Platform.isMobile` 分支（移动瓦片、全屏、长按操作菜单），且都有对应测试；
   - 首次引导在移动端直接劝退（`openSetupWizard` 开头就 return）——因为引导的内容是装 Node 与
     外部工具，手机上本来走不到终点。

ADR-0263 §5 当时的理由成立过：那时「一半功能依赖 `window.require('child_process' / 'fs')`」，
放进来是「装得上、打得开，然后一部分功能静默无反应」。但那条理由的前提是**没有兜底**；现在
各处都有兜底（`try { w.require(...) } catch { return null }`、置灰、空态），墙却还立着。

## 决策

`manifest.json` 的 `isDesktopOnly` 改回 `false`。

判断依据是「启动这一关」而不是「每个功能都完整」：

- **启动不抛**。用 `Platform.isMobile = true` + 删掉 `window.require` 的模拟环境跑完整
  `onload()` 与 `onLayoutReady` 回调（含各域 `ensure*` 真实初始化），全程无异常；
- **缺能力处都有语义**：要么置灰（影院海报、知识盒批处理），要么空态/只读（工具坞），
  要么直接说明（引导劝退）；
- 真正做不到的事（跑外部程序、装便携 Node）本来就只发生在用户显式点击的路径上，不点不触发。

同时加一条守卫 `tests/core/manifest-mobile.test.ts`，钉住三件事：`isDesktopOnly` 必须是
`false`、`main.ts` 里移动端装读桥那一支还在、`installVaultFs` 还存在。删了适配再把开关打开，
守卫会红——那正是 ADR-0263 §5 当初担心的「对大家撒谎」。

## 代价与未做的事

- 没有真机回归。模拟环境能证明「加载不抛」，证明不了「每个界面在手机上都好看」；真机走查留给
  用户，出问题按域修，不要退回去把整个插件挡在门外。
- 桌面端专属能力在手机上仍然不可用，这是设计，不是缺陷；README 的「置灰标注」承诺要保持住。
- `isDesktopOnly: false` 之后移动端也能收到自更新（走的是同一套三件套下载），手机写插件目录
  是允许的，但没在真机上验过回滚路径（`.backup/`）。若真机上更新失败，退路仍是手动覆盖三件套。
