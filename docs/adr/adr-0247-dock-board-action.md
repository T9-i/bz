# ADR-0247 · 工具坞：展示板上的动作（`#bz-act:` 回传，声明即注册）

日期：2026-10-20 · 状态：已采纳 · 关联：ADR-0243（展示板）、ADR-0244（询问框）、
ADR-0235（外部工具契约）、ADR-0239（信任边界）、`docs/dock-tool-guide.md` §4.6

## 背景

展示板（ADR-0243）一直是**只读**的：工具把结果画成 HTML，插进沙箱 iframe，人只能看。
2026-10-20 用户提出第一个「看得见也想点」的需求：

> 可以给愿望单中加入一个移除愿望单的按钮吗？有些已经买过的游戏。

直接的想法是「在 `panel.html` 里写个 `<button onclick>`」—— 不可能。展示板的沙箱
（`allow-same-origin allow-popups allow-popups-to-escape-sandbox`）**刻意不给 `allow-scripts`**，
框里的 `<script>`、`on*`、`javascript:` 一律不执行，点了没反应也不报错。

四条备选路，当场排掉三条：

| 路 | 结论 |
|---|---|
| 放开 `allow-scripts` | **否**。框里拿不到凭据（`data.json` 是 vault 里的文件）、跨域 POST 被 CORS 挡；而且与 `allow-same-origin` 同时给会让沙箱形同虚设（MDN 明确警告）—— 等于把「面板里能跑任意代码」变成每个工具产出的默认能力 |
| 加 `allow-forms` 用原生 `<form>` | **否**。没有接收端点；提交会把整个框导航走；凭据问题同上 |
| 注册 `obsidian://` 协议回传 | **否**。2026-10-20 实测：沙箱框里点 `obsidian://` 链接**毫无反应**（没给 `allow-top-navigation`，Chromium 把这类导航直接吞掉）。同一轮对照里 `https://` 链接正常打开默认浏览器 |
| 本地 127.0.0.1 小 HTTP 端点 | 可行但**不做**。为一个删单条目的动作引入常驻端口 + CSRF 面，收益与代价不成比例 |

第四条不做的同时，看到了现成的落点：`ui.ts` 的 `wireExternalLinks` **已经在干这件事** ——
展示板加载完成后，在它的 document 上以 capture 阶段挂 click 监听，拦下 `^https?://` 的链接，
`preventDefault` 后自己调 `shell.openExternal`（2026-10-20 加，为的是「外链点了没反应」）。
它拦的是「框里的一次点击」，只是当时只认 http(s)。**在这条分支上加一个前缀判断，就够了。**

## 决策

### 1. 通道：宿主挂的 click 监听，不动沙箱策略

`#bz-act:<id>?<k>=<v>` 开头的 href，在 `wireExternalLinks` 里被拦下，交给
`sandboxFrame` 的 `onAct` 回调。沙箱属性**一个字节都没改**，仍然没有 `allow-scripts`。

用 `#` 锚点而不是自定义协议，有两个好处：

- 没被拦下时（例如询问框的正文框不传 `onAct`）它退化成框内锚点跳转，**不会产生副作用**；
- 工具作者不需要知道通道长什么样 —— 将来通道换成别的，`panel.html` 一行都不用改。

安全模型是天然的：监听挂在**插件自己的** document 上，外部网页碰不到这个 iframe，
伪造不了一次点击。因此**不需要 nonce、不需要 TTL、不需要协议注册** ——
比「协议回传 + 一次性签名」那套少三个活动部件，也少三个能出错的地方。

### 2. 契约：声明即注册，`panel.html` 只写 id

```html
<a class="act" href="#bz-act:wish:remove?appid=1332010">移除</a>
```

```jsonc
"actions": {
  "wish:remove": {
    "args": { "appid": "appid" },
    "run": { "args": ["--unwish={{appid}}"] }
  }
}
```

`actions` 挂在 `manifest.json` 上（`DockManifest.actions`），解析在 `schema.ts` 的
`parseActions`，**逐条校验、坏的丢、不连累整表**（与 `params` 同口径）。动作 id 允许
`域:动词` 形态（`DOCK_ACTION_ID_RE`），它会原样出现在 href 里。

这张表里**没有一句人话**（没有 `label`、没有 `confirm`、没有「真的要删吗」）——
展示板自己画按钮和确认，脚本自己负责误删怎么补。bz 只认**参数契约**和**命令模板**。

### 3. 两道门：契约归 bz，业务归工具

起初还设计了第三道门 —— 声明里写 `confirm`，bz 弹原生确认框。**2026-10-20 用户否掉了**：

> 确认弹窗应该有展示窗自行写，点击确认后，只传参给脚本来执行即可，而不是让注册这边来做这种事情
>
> bz 侧不做什么兜底，都交给脚本做

这个切法是更干净的，理由三条：

- **确认文案只有工具作者写得准**。bz 不知道「移除愿望单」意味着什么，只能照着字段念；
  展示板自己画，就能写「这 1 款已在你库里：火线迈阿密2」，甚至按条目差异化。
- **少一个状态不同步的失败模式**。确认框说「移除 1 款」、展示板上其实是 3 款，两份状态迟早对不齐。
- **业务判断长在契约里，就等于让面板替工具做决定**。今天加 `confirm`，明天就会有人要
  「只在价格低于 X 时允许执行」—— 那是脚本的事。

所以 `DockActionSpec` 只剩两样东西：**参数契约（`args`）+ 命令模板（`run`）**。
没有 `label`、没有 `confirm`、没有任何一句人话文案 —— 那些都是展示板的事。

留下来的是两道**纯契约**的门：

1. **声明即白名单**：`manifest.actions` 里没有的 id 一律拒，不做「按链接拼参数」的透传。
2. **参数不能自由指定**：href 里出现声明之外的参数名 → 整条拒；值按类型掐
   （`appid` 只收 `\d{1,10}`；`text` 禁 `-` 开头、禁控制字符、≤200 字）。
   这是这条通道**唯一的注入面** —— 模板里写死的部分来自声明（受信任的作者），
   href 只能填 `{{...}}` 的洞。

外加一条**解析时**的自洽要求（不是运行时检查，是声明不合法就整条丢）：`run.args` 里引用了
没声明的占位符 → **整条动作丢**；没有 `run` 的动作也丢（没有命令模板，点了只能落回
「用表单参数跑一整轮」）。只丢 `run` 会退化成一个「参数被忽略、照跑不误」的空壳 ——
人点了以为在删某一条，实际跑的是完整一轮，那比失效更坏。

**确认界面怎么写**（工具作者的事，一行 JS 都不用，与表头那些 `vtab` radio 同一套路）：

```html
<input type="checkbox" id="cfm-1332010" class="cfm">
<label for="cfm-1332010" class="act">移除</label>
<div class="cfm-row">
  <span>真的从愿望单删掉？删了要手动加回来。</span>
  <a href="#bz-act:wish:remove?appid=1332010" class="danger">确认</a>
  <label for="cfm-1332010">算了</label>
</div>
```

**误删怎么补救**也是脚本的事。bz 不拦这一道，也不建议用「确认框」当保险 ——
可靠的保险是**可回滚**：脚本把动作删掉的 appid 记进 `runs.json`，下一轮在展示板上给一个
「加回来」的链接（同样是 `#bz-act:`）。

### 4. 执行：与手动运行同一条路，动作参数一次性

过了两道门之后调 `runFlow(v, { extraArgs })` —— 信任检查、必填参数校验、租约、记录、
可停止，一样都不少。`extraArgs` 拼在命令行**末尾**，且**不落进 `data.json`**：

- `values` 的形状由 `manifest.params` 决定，动作参数不在那张表里（`buildArgs` 会忽略）；
- 动作参数是**一次性**的，落盘就会变成「下次也带着这个开关」。

`DockRunOpts.extraArgs` 因此是 `runTool` 上的一个独立字段，不混进 `values`。

### 5. 不做的事

- 不给 `allow-scripts`（理由见上表）；
- 不注册 `obsidian://` / 不自建协议；
- 不引入本地 HTTP 端点；
- 不做元素级 nonce（点击本身就是一次真实交互，签名只会让「展示板重画后就失效」变成常态）；
- **不做内置动作表**。当前所有动作都落 `run`（= 跑脚本）。将来若要「打开链接」「复制文本」
  这类不跑脚本的动作，再加 `registry.ts` 那样的 handler 表 —— 现在加只是多一条没人走的路。

## 后果

**好的**

- 工具侧零依赖：一行 `<a href>`，不用知道通道、不用引 JS、不用申请权限；
- bz 侧只有三处改动：`schema.ts` 认 `actions`、`action.ts` 解析 + 掐口、`ui.ts` 的
  `wireExternalLinks` 加一条分支；
- 沙箱边界原封不动 —— 这次没有为了一个按钮松任何安全限制；
- 动作走 `runFlow` 意味着**所有既有纪律自动生效**：未信任的命令照样拦、必填参数照样校验、
  同一工具不会并发跑两份（租约）。

**要认的**

- **没有确认这道保险了**。bz 不弹框、不问「真的要删吗」。某个工具忘了在展示板上画确认行，
  就是一点即删 —— bz 拦不住，也不会提示。这是「业务归脚本」的必然代价，接受它。
- **审计靠工具自己写**。`runs.json` 由工具写（四行协议），bz 不额外记「谁点了哪个动作」。
  工具**必须**把「这次做了什么」写进 step / result（例：「从愿望单移除 1 款：火线迈阿密2」），
  否则记录里只剩一条和手动运行长得一样的 entry。
- **可逆性也归脚本**。真要防误删，靠的不是确认框，是「删了能加回来」：把动作删掉的东西记进
  记录，下一轮在展示板上给一个反向动作的链接。
- **展示板重画后动作仍然有效**（因为不需要 nonce），但按钮对应的条目可能已经不在列表里 ——
  动作是否还成立由声明和脚本判，bz 不做二次核对。

## 补记

- 2026-10-20 首次落地：`action.ts`（解析 / 掐口 / 模板）+ `schema.parseActions` +
  `wireExternalLinks` 分支 + `runFlow` 的 `extraArgs`。
  首个消费者是白菜价雷达的 `wish:remove`（面板上逐款移除已买过的游戏）。
- 2026-10-20 同日修订：**删掉 `confirm` 字段与 bz 侧确认框**（用户拍板：确认界面归展示板、
  兜底归脚本）。契约从「三重门」收成「两道门 + 解析期自洽」，`actDetailText` / `confirmAct`
  一并删除 —— 这是一次净减法，验证了「把业务判断挡在契约外」不是空话。
- 同一轮实测记录（写给后来的人，免得再试一遍）：沙箱 iframe 里 `https://` 链接能开
  （`wireExternalLinks` 生效）；`obsidian://` 链接点了**毫无反应**；`store.steampowered.com`
  的心愿单网页端点带 cookie 会 429、不带 cookie 跳首页 —— 删愿望单只能走
  `IWishlistService/RemoveFromWishlist`（POST，`access_token` + `steamid` + `appid`，实测 200）。
