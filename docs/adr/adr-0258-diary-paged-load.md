# ADR-0258 日记本按窗读盘：一册一窗，翻到册尾再续

- 日期：2026-10-25
- 状态：**已被 ADR-0259 取代**（2026-10-25：分窗省的是读盘，慢的是 DOM；索引/检索被裁到窗口内）
- 相关：ADR-0170（墙数据预热 / 四目录并行 / 会话级缓存）、ADR-0171（开册进度条）、ADR-0231（撤销的「首屏窗口化」）、ADR-0233（书内写作页）、ADR-0064（声明式设置 schema）

## 背景

日记正文是**一篇一个文件**（ADR-0130/0131），开册要把它们全部 `vault.read` 一遍再整册分页建书。
篇数以千计时这不是「稍微慢一点」：1243 篇正文的磁盘读 + 每批 10 的串行批次要好几秒，
接着是整册测量切页 + StPageFlip 一次建几百页——这台机器在这两段里都是被占住的，
人对着空书等，桌上一张报进度的纸条陪着。

用户点名：**「日记本，加载五十条数据即可，不用一次性加载所有的」**，追问后追加
**「五十页快翻完了，继续加载五十页」**——要的是「翻到哪儿读到哪儿」，不是先排一小批、
读完后台再偷偷重排（那是 ADR-0231 撤销的那套，观感上是「书自己变厚」）。

## 决策

1. **两段式读盘：先定全序，再按窗读正文。**
   - 日记的全序不必读正文：题目就是 `YYMMDDHHmm`，`diaryMetaFromEntryPath` 从文件名就能取出日/时；
   - 影视 / 书本来只读 frontmatter（`parseMovieFile` / `parseBookFile` 不碰正文），信要读正文但通常没几封——
     三类**一次解析齐**，当另一条降序游标；
   - 于是「四类混排」的次序在首窗那一刻就确定了，正文只是按窗往里补。
     `pickWindow` 每次从两条游标里取更新的那一条，交给 `pullWindow` 按 10 并发读。

2. **一窗 = 设置项 `diaryPageSize`**（`src/settings.ts`，缺省 50；设置面板「日记本 → 显示 → 每次翻开多少则」，
   夹 10–500）。写死常量会让「我这台机器一次看全」没法表达，故留成设置。

3. **续读由人翻到册尾触发。** 离册尾 2 页内（`LOAD_MORE_AHEAD_PAGES`）预取下一窗，读到的旧条目接在册尾。
   接完按**绝对页号**落回原来那一页：册页数是这次才变多的，按比例落页会把人推到新册尾，
   等于「一翻到底就被踢到最旧那一页」。

4. **回源补齐（`wallAsked`）。** 域事件 / 手动刷新会作废缓存，重读时按「上次已经读到第几则」补齐——
   深翻到第 200 则被人改了篇日记，册子不该缩回 50 则、把人正读的那页抹掉。
   `invalidateWallCache()` 只作废缓存、不清已读条数；只有换 app 才整轮重来。

5. **哪些不算「人翻到册尾」**：建书期的程序化 `turnToPage`（库也会发 `flip`，不掐掉会自触发一路读完整墙）、
   以及纸上摊着草稿的时候（续读要整册重排，那张没落笔的纸不能被换走）。

6. **进度条口径跟着改**：读数从「日记正文篇数」改为「这一窗的条数」（四类合计），
   与紧接着的「正在装订… 共 N 则」同一个 N，不再出现「30 / 30 篇」后面接「共 27 则」的自相矛盾。

## 后果

- 开册时间与总篇数**脱钩**，只与窗口大小成正比；一本几千篇的日记本开起来和五百篇差不多。
  代价是册子一开始薄薄一叠（50 则铺开仍是一两百页），翻到册尾才变厚。
- **台历、册页索引、放大镜检索、贴纸册计数只看已读的那一段。** 旧行为「一次覆盖全部历史」不再成立：
  越往旧日子翻，这几处覆盖越全。这是分窗最实在的代价，接受它是因为用户要的就是「不必一次读全」。
- 深翻后被外部改动逼着回源，代价 = 已读条数（仍远小于旧实现的「每次刷新都全量重读」）。
- 想「一开册就看全」把它调到 500 即可，不需要改代码、更不需要退回全量实现。

## 备选（未采纳）

- **首屏先排一小批、读完后台再重排**：ADR-0231 已撤销的正是这套，用户当年明确否掉「书自己变厚」。
- **只裁日记、三类照旧全读**：三类本来就不读正文（信除外，且量小），省不下关键开销；
  而混排次序还需要它们的日期，裁了日记反而要先知道其余三类的日期——不如统一按窗。
- **按天数（一天一页）分窗**：条目密度不可控（一天可能十篇、也可能一个月一篇），页数与读盘量都对不上。
