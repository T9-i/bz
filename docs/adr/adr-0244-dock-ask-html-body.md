# ADR-0244 · 工具坞：询问框的正文可以是工具画的 HTML（复用展示板那套沙箱 iframe）

日期：2026-10-15 · 状态：已采纳 · 关联：ADR-0235（外部工具契约）、ADR-0243（展示板）、
`docs/dock-tool-guide.md` §4.5

## 背景

运行中询问（`[bz-ask]` 出去、`[bz-answer]` 回来）是给「必须经人点头才能做的动作」开的一条回程：
工具跑到一半弹一框问一句，人点确认它接着做。上线后第一个真吃它的工具是 steam-classify
（把 Steam 库里没归类的游戏写进收藏分类，写之前得先关掉 Steam）。

那一框要摆的是**一张核对表**：四款游戏分别进哪个分类（分类 → 游戏名，按分类分组）。
`BzAskRequest.body` 只能按 `\n` 分段渲染成几段散文 —— 排出来是一堆挤在一起的字，人没法核对，
只能盲签。用户的原话：

> 这个弹窗，里面的内容也由脚本写 html 可以自定义样式布局，可以做的精美好看些。

也就是：**这一块内容该由工具自己画**，bz 不该替每个工具设计版式 —— 与展示板（ADR-0243）同一个
动机，只是落点从「详情页的一块区域」变成「弹窗里的正文」。

## 决策

### 1. 协议加一个可选字段 `bodyHtml`，`body` 留着当兜底

`[bz-ask]` 的体里多一个 `bodyHtml`（字符串，trim 后非空即**优先**）。两样都给时 HTML 胜，
`body` 不退场：它进记录、也是 HTML 被退回时的兜底文本。

**不是「把 `body` 改成收 HTML」**：那等于让所有现存工具的下一次输出自动升级成 HTML ——
它们写的是纯文本（可能带 `<` `>`，比如打印一段 diff），当 HTML 渲染就是内容变形。
两条路各说各的，工具自己选。

### 2. 渲染用沙箱 iframe，与展示板同一套

`<iframe sandbox="allow-same-origin">` + `srcdoc`，**不给 `allow-scripts`**。

理由与 ADR-0243 完全相同（工具输出是外部进程的产物、`<style>` 会串色、没闭合的标签会吃掉
后面的 DOM、`allow-same-origin` 只为量高度），此处不重复论证。这里只补一条**这一处特有的**：

**按钮与倒计时不在框里。** 框里只有「那一块内容」，`confirmText` / `cancelText` 只能改那两个钮
上写的字。回程（`[bz-answer]`）是 bz 独占的通道 —— 让工具自己画钮、自己编一条回程消息，
等于把「这一下要不要做」的答案判据交给被问的那一方。

### 3. 尺寸：字节 128 KB 封顶，高度不封顶，框宽 560

- **字节 128 KB**：一个弹窗正文不该有展示板那么大（那是把该写进手册的东西塞进来了）。
  超了**退回纯文本 `body` 并在框里说明原因** —— 这一点与展示板刻意不同：展示板不渲染 ≠ 没内容，
  而询问框「没有正文」等于让人对着一个空框拍板。所以宁可退到能读的东西，也不能静默。
- **高度不封顶，滚动归正文区**（2026-10-15 修订，见「补记」）：框跟着内容长，超一屏时由
  `.bz-dock-ask-pane` 滚 —— 滚动条于是是宿主的（细、跟主题），按钮行钉在下面。
- **框宽**：纯文本仍 460 px，HTML 560 px。工具常要摆一张表，多这点宽度能明显少折行；
  纯文本那份没有版式可摆，宽了只是把一行字拉长。

### 4. 主题注入与量高逻辑与展示板共用一份实现

`frameBaseStyle()`（灌主题变量 + 基线）/ `fitFrameHeight(frame)` / `sandboxFrame(...)`
提到共用位置，两个消费者共用。**两份会漂**：观感对齐宿主这件事只要有两份实现，迟早一份改了
另一份没改，而症状是「展示板跟得上主题、弹窗跟不上」这种没人会立刻查觉的偏差。

### 5. 主题变量只给那一小撮

沿用 `BOARD_THEME_VARS`（底色 / 文字 / 描边 / 品牌色 / 圆角 / 字体 / 间距）。给全套等于把面板内部
token 变成公开 API —— 日后重构得先问过所有工具。

## 后果

- 工具能画自己的确认版式（表格、分组、状态色）；steam-classify 的弹窗由此从「一段散文」变成
  「分类 → 游戏名」的表格。
- bz 侧多了：解析一个字段、一条 iframe 渲染路径、两个上限常数；`dock/ui.ts` 里展示板那三个私有
  函数改成共用（名字从 `board*` 改成 `frame*`）。
- 询问框的**语义**没变：超时仍是取消、没人在场仍是取消、按钮仍归 bz。

## 刻意没做

- **不给 `allow-scripts`**，哪怕「写脚本的人本来就能在本机跑命令」—— 那条口子日后一定会被当成
  「弹窗里能塞会跑的代码」的能力去用。
- **不让工具自定义按钮或回程形状**（见决策 2 末段）。
- **不做「HTML 里引用 panel.html」**：那份是常驻的现状文件，弹窗正文是这一次运行说出来的话，
  性质不同；真要共用观感，共享的是主题变量，不是文件。

## 补记（2026-10-15 · 高度上限废掉，滚动交回宿主）

第一版给框封了高度（询问框 360 px、展示板沿用 ADR-0243 的 520 px），超出部分**让框自己滚**。
当天用户就报了症状：

> 确认弹窗和展示窗口都不显示滚动条。

「不显示」= 两个框里都**别**长滚动条。而框自己滚出来的那根是**原生**的：界面管不着它、它也不跟
主题（Windows 上还带上下箭头），跟宿主的细滚动条完全不是一回事 —— 与「展示板样式只能影响框内」
是同一个道理的另一面：**框内的一切都归宿主管不着**，那就该让框里没有需要滚的东西。

改成**框跟着内容长**（`fitFrameHeight` 不封顶），滚动交给外面那层：

| | 谁滚 | 滚动条 |
|---|---|---|
| 展示板 | 面板内容区 `.bz-dock-body`（本来就有） | 宿主的 |
| 询问框正文 | 新增的 `.bz-dock-ask-pane` | 宿主的 |

询问框那边照抄 `memo` 编辑弹窗那一套（`.bz-memo-editor-popup` 的注释写着同一个结论：**「弹窗
整体不再滚 —— 滚动移交内容区，保存钮行才能钉底」**）：弹窗 `overflow:hidden` → 正文区
`flex:1 1 auto + overflow-y:auto` → 动作行留在滚动区外，于是按钮与倒计时永远在手上。

字节上限（512 KB / 128 KB）不动 —— 那管的是**体积**（灌进 srcdoc 的开销、以及「别把手册塞进
展示板」），与滚不滚没关系。代价要认：展示板理论上能长到任意高，所以它仍是「一眼看完的几行数」。
