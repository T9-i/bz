# 544 · iamtxt 签到成功却弹「失败」通知 —— 通知只看退出码，从没读过工具自己的记录

## 症状

iamtxt 每日签到实际签成了（站内确实签了、工具自己写的记录也是 `ok`），但工具坞弹出一条：

```
iamtxt 每日签到 失败：查看运行记录里的 stderr 尾部定位
```

「查看运行记录」这句话指向的那份记录里，写的恰恰是**成功**。通知和它对不上的时候，
用户没有任何办法自己判断该信哪个。

## 根因：`classify()` 注释承诺了「以记录为准」，代码从没实现

`src/dock/runner.ts` 里 `classify()` 的注释原话：

> 注意：这是 bz 侧的**推断**，供在场运行时立刻给出可操作提示；权威分类在工具自己写的运行记录里
> （`error.kind`）。**两者不一致时以记录为准** —— 工具比 bz 更知道自己死在哪儿。

但 `classify()` 只接收 `ExternalToolOutcome`（退出码 / stopped / stderr），**根本没读过记录**：
`runner.ts` 全文没有任何读取 `runs.json` 的代码（唯一的读取方是 `data.ts` 的画面板与
`watch-core.ts` 的值守侧）。于是「工具记录写着成功、进程却以非零码退出」（或反过来）时，
通知讲的是错的那一边 —— 而 `errorHint('unknown')` 的兜底文案还把人支去「看运行记录里的
stderr 尾部」，等于让他去核对一份**与自己矛盾**的文件。

## 查证过程（与结论一起记，免得下次重走）

1. 工具自己的账本：**29 条记录全部 `status: ok` / `exitCode: 0`**，历史上零失败
   （`runs.json` 里唯一那条 failed 是本次排障时我手跑出来的，已清掉）。
2. bz 侧的台账 `runState` 停在更早的一次成功，**没有失败计数 / 熔断标记** —— 按代码，
   手动路径失败本来就不写台账，所以这条不能反证什么，只能说明「失败没留下 bz 侧痕迹」。
3. 按 bz 的原样（同 cwd、同 argv 形状、同**整体替换掉的**环境、`shell: false`）**连跑 5 次**：
   退出码 `0/0/0/0/0`，记录 `ok`，四行协议完整（7 行都在）。
   **复现不出那次非零退出。**
4. 因此结论落在**能证的那一半**：不论那次退出码为什么非零，bz 都**不该**只看退出码就下判决 ——
   它自己在注释里也是这么写的。

## 修法

新增 `reconcileWithRecord(outcome, declPath)`，在 `run.done` 里、`cb.onDone` 之前对一次账：

- **只认属于本次运行的那条**：记录 `startedAt` 不早于本次起跑时刻（留 2s 余量吸收时钟/落盘次序）。
  拿不到、解析不出、时间对不上 —— 一律原样返回 bz 的推断，**绝不拿上一条记录充数**：
  把上一次的成功报成这一次的结果，比误报一个字更糟。
- 同一次起跑留了多条 → 取**最晚**那条（后写的才代表最终结论）。
- **`stopped` 不参与对账**：用户点了停止就是停止，工具写了什么记录都不改变「是他掐的」。
- 三种「没有记录」被区分开，因为对通知含义不同：
  - `recordStatus: null` = **这次运行没留记录**（记录文件读到了，里面没有本次）→ 通知改口径；
  - `recordStatus: undefined` = **问不出**（文件读不到 / 坏 JSON / 没有 fs）→ 保持原样不猜。

`notifyRunOutcome` 里失败的提示语相应分岔：记录里**根本没有这次运行**时，不再说
「查看运行记录里的 stderr 尾部定位」（那份记录不存在），改说
「工具没留下这次运行的记录，多半没跑到写记录那一步；它的启动报错在控制台」。

## 没做

- **没改 iamtxt 工具的 `trigger` 写死**：它的 `finish()` 里 `trigger: 'auto'` 是硬编码，
  没读 `BZ_DOCK_TRIGGER`（契约里那个变量的用途就是给它标 trigger）。所以它 29 条记录里的
  `trigger` 字段全是错的（手动跑也记 auto）。属**工具侧**的另一处缺陷，独立开票。
- 没动 `classify()` 的推断本身：它作为「立刻给一句可操作提示」的第一层判断是对的，
  缺的只是后面这道对账。

## 验证

- `tsc --noEmit` 干净；
- `tests/dock/runner.test.ts` 新增 7 项（12 项全过）：记录说成功→撤回失败推断、记录说失败→
  改用记录的 `error.kind`、记录早于本次→不认、本次没留记录→`null`、坏 JSON→原样、
  stopped 不参与、多条取最晚；
- 全量 `node scripts/test-affected.mjs --full`：596 文件 / 9207 项通过 / 2 跳过。

## 还没能回答的

那次真实的非零退出**为什么发生**，没有证据可查（那次运行没在任何一份记录里留下痕迹）。
本票修的是「不该只看退出码」这条判据错误 —— 修完之后，即使同样的非零退出再发生，
通知也会以工具自己的记录为准，不会再出现「说失败、记录说成功」的对不上。
若它再犯且记录里也没有本次运行，新文案会直接说明这一点，指向「工具没跑到写记录那一步」。
